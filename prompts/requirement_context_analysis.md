# 需求与接口文档上下文分析

## 目标

当用户提供 PRD、需求文档、接口文档、OpenAPI/Swagger 或相关链接时，提取测试影响分析所需的业务与接口上下文。该步骤是可选项：没有文档时不阻塞后续 diff 和代码分析。

## 支持输入

可接受以下形式：

- 本地 Markdown、TXT、YAML、JSON、HTML、PDF、Word 文档路径。
- PRD、需求说明、验收标准、测试范围说明。
- 接口文档、OpenAPI/Swagger 文件或链接。
- Confluence、飞书、语雀、GitHub 文档等链接。

如果链接需要联网或权限，先确认是否可访问；无法访问时记录限制，不要编造文档内容。

## 提取内容

优先提取与本次 PR 变更相关的内容：

1. 业务目标
   - 本需求要解决的问题。
   - 新增、修改或删除的业务能力。
2. 功能点
   - 主要流程。
   - 分支流程。
   - 异常流程。
   - 角色、权限、租户或组织隔离要求。
3. 验收标准
   - 明确的通过条件。
   - 必须支持或禁止的行为。
   - 边界值、兼容性和历史数据要求。
4. 接口契约
   - HTTP 方法、路径、请求参数、请求体。
   - 响应结构、错误码、状态码。
   - Header、鉴权、签名、租户字段。
5. 字段约束
   - 必填、长度、格式、枚举、默认值。
   - 金额、数量、时间、状态类字段边界。
6. 数据与依赖
   - 数据准备条件。
   - 数据落库或查询要求。
   - 外部系统、消息、定时任务、缓存、配置开关。

## 与代码变更对齐

将文档内容和 diff / 本地代码建立映射：

```text
文档功能点 → Controller 接口
文档字段约束 → DTO / 校验注解
文档业务规则 → Service 方法
文档数据要求 → Mapper / Repository / Entity
文档配置要求 → application.yml / 配置类
文档验收标准 → 测试用例与回归范围
```

如果文档和代码不一致，必须记录：

- 文档描述。
- 代码实际表现。
- 不一致风险。
- 需要产品、研发或测试确认的问题。

## 输出到后续分析

不要强制生成独立文件；可以在报告中形成“需求 / 接口文档依据”章节。若需要结构化记录，可写入 `impact.json` 的补充字段或在报告中直接引用。

推荐结构：

```json
{
  "requirement_context": {
    "sources": [],
    "business_goals": [],
    "features": [],
    "acceptance_criteria": [],
    "api_contracts": [],
    "field_rules": [],
    "document_code_mismatches": [],
    "uncertainties": []
  }
}
```

## 文档关卡 Harness（关卡检查）

文档存在时检查：

```text
□ 文档来源已记录，包括路径或链接
□ 文档可访问；不可访问时已记录原因
□ 已提取业务目标、功能点、验收标准或接口契约
□ 文档内容已尝试和 diff / 本地代码建立映射
□ 文档和代码不一致时已列为人工确认项
```

文档不存在时检查：

```text
□ 已记录“未提供需求/接口文档”
□ 报告中说明业务验收标准只能从代码和 diff 推断
```
