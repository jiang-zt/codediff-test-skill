# 中文 Markdown 报告生成

## 目标

生成面向中国测试团队的中文 Markdown 测试影响分析报告。报告应能帮助测试人员判断测什么、为什么测、优先级是什么、依据在哪里。若提供 PRD、需求文档或接口文档，报告必须体现文档依据；未提供时说明边界。

## 推荐工具

```bash
python3 tools/report_builder.py \
  --impact-json output/<featureID>/impact.json \
  --output output/<featureID>/test-impact-report.md
```

如果工具生成内容不完整，agent 应结合 `impact.json` 和本地代码阅读结果补充报告。

## 必需结构

```markdown
# PR 测试影响分析报告

## 1. PR 基本信息
## 2. 分析范围与前提
## 3. 需求 / 接口文档依据
## 4. 变更摘要
## 5. 变更文件分类
## 6. 本地代码上下文阅读结果
## 7. 受影响接口
## 8. 接口测试用例建议
## 9. 业务回归范围
## 10. 数据库 / 配置 / 依赖风险
## 11. 建议补充的自动化测试
## 12. 不确定项与人工确认项
## 13. 测试结论建议
```

## 内容要求

- 全文使用中文。
- 重要结论必须引用文件路径、接口路径、方法名或 diff 来源。
- P0 项放在 P1/P2 前面。
- 测试建议必须和实际变更绑定，不写空泛建议。
- 不确定项单独列出，不要混在结论里。
- 如果没有本地项目路径，必须在“分析范围与前提”中说明局限。
- 如果有本地项目路径，必须说明已阅读哪些关键文件或模块。
- 如果提供了 PRD / 需求 / 接口文档，必须在“需求 / 接口文档依据”中列出来源和测试相关结论。
- 如果未提供文档，必须说明“未提供需求/接口文档，业务验收标准主要从代码和 diff 推断”。
- 如果文档和代码不一致，必须写入“不确定项与人工确认项”。

## 推荐表达

优先使用测试人员可执行的表达：

```text
建议重点验证 POST /orders 的正常创建、重复提交、库存不足和权限不足场景。
证据：OrderController#createOrder、CreateOrderRequest、OrderService#create。
```

避免没有依据的表达：

```text
需要全面测试订单模块。
```

## 报告关卡 Harness（关卡检查）

交付报告前检查：

```text
□ 报告为中文
□ 报告已写入 output/<featureID>/test-impact-report.md，除非用户指定了其他目录
□ 包含 PR 信息、分析前提、需求/接口文档依据、变更摘要、接口、用例、回归范围、不确定项
□ 每个核心建议都有证据
□ 如提供文档，报告中已引用文档依据；如未提供，已说明文档缺失边界
□ P0/P1/P2 层级清楚
□ 没有把推测写成事实
□ 已说明本地代码是否参与分析
```

## 交付

交付时说明：

- Markdown 报告路径。
- 可选资产路径。
- 未能确认或需要用户补充的信息。
