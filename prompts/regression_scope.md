# 回归范围生成

## 目标

将代码影响面转换为 P0/P1/P2 回归计划，说明哪些必须测、哪些建议测、哪些可抽样测，以及为什么。

默认基于 `output/<featureID>/impact.json`、本地代码阅读结果，以及可选的 PRD / 需求 / 接口文档生成回归范围。

## 优先级规则

P0 必测：

- 直接变更的 Controller 接口。
- 直接承载核心业务规则的 Service 方法。
- 可能破坏客户端兼容性的 DTO 字段或校验规则变化。
- 影响核心读写的 Mapper、Repository、SQL。
- 影响启动、环境、依赖冲突的配置或依赖变化。
- 变更涉及支付、订单、资金、权限、用户身份、数据写入、审批流等高风险业务。
- PRD 或验收标准明确要求必须覆盖的核心流程。
- 接口文档明确变更的请求/响应契约。

P1 建议测：

- 同一 Controller 下的邻近接口。
- 调用同一 Service 或共用 DTO 的接口。
- 下游 Feign、RPC、消息生产/消费、定时任务。
- 查询条件、分页排序、历史数据兼容。
- 与变更模块共享公共工具、拦截器、过滤器或配置的路径。
- 文档中提到但代码变更未直接命中的相关业务流程。

P2 抽样测：

- 共享基础能力但没有直接证据表明受影响的接口。
- 非核心展示或查询路径。
- 低风险重命名、注释、日志、格式调整。
- 构建类或测试类变更的辅助验证。

## 输出矩阵

报告中使用以下矩阵：

```markdown
| 优先级 | 回归范围 | 纳入原因 | 建议检查 | 证据 |
|---|---|---|---|---|
| P0 | ... | ... | ... | ... |
```

## 风险类别

按以下类别归纳：

- API 契约风险
- 业务规则风险
- 数据一致性风险
- 客户端兼容风险
- 环境 / 配置风险
- 依赖 / 构建风险
- 测试覆盖风险
- 权限 / 租户 / 鉴权风险

## 回归边界

必须明确说明：

- 纳入回归的范围和原因。
- 暂不纳入的范围和依据。
- 依据不足但建议人工确认的范围。
- 文档和代码不一致导致需要确认的范围。

不要把证据不足的内容直接排除。证据不足时应写成“暂未确认”或“建议人工确认”。

## 回归关卡 Harness（关卡检查）

生成回归范围后检查：

```text
□ P0/P1/P2 已分层
□ 回归范围基于 output/<featureID>/impact.json 或本地代码证据
□ 每个 P0 都有直接证据或高风险业务理由
□ 排除范围有依据，不是静默忽略
□ 配置、依赖、数据库、权限、兼容性风险已考虑
□ 如提供文档，文档中的验收标准和接口契约已纳入回归判断
□ 如未提供文档，已说明回归范围主要来自 diff 和本地代码
□ 不确定范围已进入人工确认项
```
